# Roamlet

An account-free, local-first cycling and hiking route planner.

## Local-first workflows

Roamlet keeps routes, preferences and the current unsaved draft on this device. No account, analytics or cloud synchronization is required; local workflows need no backend. **Export** opens a dialog with the route name, activity, distance, original time estimate, available ascent/descent, and separate counts of track points, GPX segments and waypoints, followed by an editable GPX filename and a download action. Elevation metrics require complete heights and an eligible GPX/ORS source; missing or partial heights are not invented. The summary adapts to small screens. Filename edits do not rename the route or change its geometry; GPX preserves existing track segments, available elevations, and waypoints. Separate collapsed Komoot and Strava guides link to official import instructions: import is manual, with no account connection or automatic upload. The Strava guide describes creating a route on the website, not uploading a completed activity, and notes that route creation may require a subscription. Downloading works offline; opening external help or Komoot requires internet. GPX is not a full backup of the editor or local library. Automatic routes and loops still use the existing OpenRouteService integration; manual drawing, GPX and library operations remain local.

Automatic routing uses hosted OpenRouteService (ORS) through a same-origin server proxy at `/api/route`. The browser never receives the provider API key. MapLibre GL JS with OpenFreeMap supplies basemaps; manual straight-line planning remains local and independent of ORS and its API key. Only routing requires Vercel Functions; no application database, external draw plugin or offline basemaps are added. Manual geometry uses the existing MapLibre GeoJSON rendering and statistics pipeline. See service-dependent limitations below.

“Report a map issue” is available in the map’s “More map tools” (⋯) menu on desktop and mobile, rather than as an overlay on the map.

## Development

Use Yarn 4.18.1 (the latest stable release verified on 28 October 2026), pinned in `packageManager` and bundled in `.yarn/releases`. `.yarnrc.yml` selects the standard npm registry and the familiar `node_modules` linker. Corepack uses the pin; existing Yarn Classic installations forward to the bundled release via `.yarnrc`. Without either launcher, use `node .yarn/releases/yarn-4.18.1.cjs` instead of `yarn`:

```sh
yarn install --immutable
cp client/.env.example client/.env.local
cp .env.example .env.local
# For routing only, set ORS_API_KEY in root .env.local (never commit actual keys)
# Optionally set VITE_MAP_STYLE to an http(s) or root-relative style URL
yarn dev
```

Requires Node.js 24+ and the pinned Yarn release. `.nvmrc` selects Node.js 24 LTS (`nvm install && nvm use`); newer Node.js versions are also supported. Yarn’s default install-script restrictions remain in place; only esbuild’s required build script is explicitly allowed via `dependenciesMeta`. OpenFreeMap basemaps require no routing key. Configure server-only `ORS_API_KEY` in root `.env.local` for hosted OpenRouteService routing. Never use a `VITE_` prefix for secrets. The value is trimmed and must be nonempty; no Mapbox `pk.*` prefix is required. Never commit actual API keys. Restart Vite after changing the server key; on Vercel redeploy after changing server environment variables. Public `VITE_MAP_STYLE` changes require a restart or rebuild. A missing key disables automatic routing and loop discovery only, not the map, manual planning, local library, coordinate/map input or GPX workflows. Create a key in the [HeiGIT account dashboard](https://account.heigit.org/) and review current quotas and service terms. Paid geocoding and terrain services are not used.

`yarn dev` starts the client Vite server at `http://127.0.0.1:5173` with local API middleware using the same server handlers as Vercel. `yarn preview` includes this middleware too. Public map settings live in gitignored `client/.env.local`; the server key lives in root `.env.local` (or the process environment, which takes precedence). Basemaps remain browser-direct; routing goes through `/api/route`. `/api/routing-config` returns only `{ "available": true/false }` with no secret. No client-visible ORS key is needed.

### Production: Vercel static frontend and routing functions

```sh
yarn build
# Inspect the existing build locally:

# Equivalent:

```

`yarn build` produces static assets in `client/dist`. Both `yarn start` and `yarn preview` run Vite preview at `http://127.0.0.1:4173`; they require an existing build and are local preview commands, not production hosting. Deploy the repository on Vercel at the origin root using `vercel.json`: Root Directory is the repository root, Node.js is 24.x, and Output Directory is `client/dist`. Vercel deploys the root `api/*.mjs` functions alongside the static frontend; uploading only `client/dist` elsewhere does not include routing. No application database is needed. HTTPS is required outside localhost for the offline app shell.

#### Server key and public API protection

1. Create an ORS key in the [HeiGIT account dashboard](https://account.heigit.org/).
2. In Vercel **Settings → Environment Variables**, add **Sensitive** `ORS_API_KEY` for Production, then redeploy. Use a separate key for Preview or leave routing disabled there. Remove any old `VITE_ORS_API_KEY`; rotate keys previously shipped in a browser build.
3. Before public access, configure **Vercel Firewall** rate limiting on path `/api/route`, method POST. Set per-client limits according to the account's current quotas; loop discovery can make up to six calls, and mixed routing can make multiple calls. Availability of Firewall rate-limiting rules depends on the Vercel plan; verify support before launch. This repository intentionally has no unreliable in-memory limiter and does not automatically configure Firewall.
4. Monitor aggregate ORS daily/per-minute usage and Vercel function usage; IP limits are not an account-wide budget. Restrict deployment access or disable the key if protection or quota monitoring is unavailable. Do not log coordinates, keys or raw upstream errors.
5. Verify two real deployments: service-worker update, draft recovery, routing and offline/manual workflows. Test the permanent production domain before users save routes; browser storage is origin-specific.

The proxy accepts only four cycling/hiking profiles, 2–25 longitude/latitude points, the supported ferry/step avoidance options and bounded point alternatives. It enforces a 16 KiB request-body limit, an 8 MiB upstream-body limit, a 4 MiB final serialized JSON response limit (leaving headroom for Vercel), and a 20-second timeout covering both the provider request and response-body consumption. It sanitizes responses/errors, disables API caching and rejects cross-origin browser requests. These checks protect the key and constrain requests, but **do not replace Firewall rate limits**. Maps and GPX stay client-side.

#### API implementation and error contract

The files in `api/` remain thin Vercel entry points. Shared implementation lives outside that directory:

- `server/routing.mjs`: HTTP handlers and metadata-only request logging; `createRoutingHandlers` accepts an API-key getter, ORS client and logger for isolated tests.
- `server/routing-contract.mjs`: input validation and sanitized GeoJSON output.
- `server/routing-http.mjs`: bounded body parsing, same-origin checks and JSON responses.
- `server/ors-client.mjs`: provider transport, bounded stream consumption and cancellation; `createOrsClient` accepts a fetch implementation and timeout.
- `server/routing-config.mjs`: server-only environment access.

Vite development/preview middleware and Vercel entry points use the same default handlers. Endpoint URLs and successful response shapes are unchanged. Errors use `{ "error": { "code": "…", "message": "…" } }`; ORS codes `2004`, `2009` and `2010` remain numeric for route-limit/no-route handling.

| HTTP status     | Application code                                                            | Meaning                                                                 |
| --------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 400 / 413 / 415 | `INVALID_REQUEST` / `REQUEST_TOO_LARGE` / `UNSUPPORTED_MEDIA_TYPE`          | Rejected input                                                          |
| 403 / 405       | `FORBIDDEN` / `METHOD_NOT_ALLOWED`                                          | Origin or method rejected                                               |
| 400 / 404 / 422 | Safe numeric ORS code or `INVALID_REQUEST` / `UPSTREAM_REJECTED`            | Provider rejected the route request                                     |
| 502             | `UPSTREAM_UNAVAILABLE` / `UPSTREAM_RESPONSE_TOO_LARGE`                      | Provider/network/response failure                                       |
| 503             | `ROUTING_NOT_CONFIGURED` / `UPSTREAM_UNAVAILABLE` / `UPSTREAM_RATE_LIMITED` | Missing key, provider credentials rejected, or provider quota exhausted |
| 504             | `UPSTREAM_TIMEOUT`                                                          | Provider exceeded the time budget                                       |

Provider `401`/`403` responses are not forwarded as user authorization failures. Provider `429` becomes `503` with `UPSTREAM_RATE_LIMITED`; the browser still reports quota exhaustion and does not retry loop candidates. Firewall-generated `429` remains a separate deployment-level rate limit, handled by the browser by status regardless of response format.

Each route request returns a server-generated `X-Request-Id`. Structured function logs contain only the event name, that ID, duration in milliseconds, final HTTP status and a fixed outcome category. Coordinates, keys, request bodies and raw provider errors are excluded. Logging failures do not change the response. API caching remains disabled; no shared route cache or application database is introduced.

## Implemented workflows

- MapLibre GL JS (maplibre-gl 5.x) map with OpenStreetMap Standard raster tiles by default (`/osm-standard.json`) and an alternate style labeled Light (`https://tiles.openfreemap.org/styles/bright`), with no separate Custom option. The picker order is Standard (map icon), then Light (Bright, sun icon); Russian labels are «Стандартная» and «Светлая». A configured `VITE_MAP_STYLE` provider occupies the Standard slot instead of exposing a user-facing custom-map mode; configuring Bright keeps OSM in the Standard slot. Satellite mode is not exposed. Switching styles preserves the camera and restores actual route geometry and numbered pins. Required OpenStreetMap/OpenMapTiles style-source attribution, zoom/pan, fit-to-route, optional user location, click-to-add, and draggable waypoint pins remain available; no Mapbox renderer logo is needed. Desktop route fitting accounts for the floating planner’s footprint. No unsupported map layers or offline basemap downloads are exposed.
- Initial viewport priority: opened route → locally saved map view → approximate browser timezone/locale region → world overview. Known IANA timezones select a regional view, other supported continent timezones select a wider view; otherwise locale country/language is a fallback. Browser settings are **not actual geolocation** and may be unrelated to the user's position. No IP lookup, inference API, or automatic location permission prompt is used.
- Completed map movements save center, zoom, bearing and pitch under `roamlet:map-view:v1` in localStorage. Saved views take priority on reload, while opening/importing a route still fits its geometry. Malformed stored views are ignored; blocked/quota-limited storage does not prevent map use and shows a nonfatal save notice. Clearing site data resets the preference.
- Automatic point-to-point routing with up to 25 stops; coordinate/map replacement, reorder, remove, reverse and cancellable recalculation. Cycling offers ORS regular, road and mountain profiles; hiking uses `foot-hiking`. Avoid-ferries and avoid-steps options apply to automatic sections, not manual lines. These preferences do not guarantee actual surface or access. The application retains its 25-point limit even if hosted ORS allows more. Existing longer ORS/legacy Mapbox/GPX snapshots remain readable/exportable, but automatic editing requires reducing stops to this limit.
- Point-to-point sections can individually use automatic road/path routing or an explicitly unverified direct line. Adjacent automatic sections are batched to limit requests. Direct geometry remains separate, uses no invented connectors or heights, and is highlighted differently on the map. Outgoing section modes, routing preferences and direct geometry survive drafts, library backups and history; the last stop's outgoing mode is ignored. Reversing preserves the original sections' modes, and inserting a stop inherits the split section's mode. Mixed time combines ORS durations with average-speed estimates for direct sections.
- Manual planning is activated by the ruler-icon button in `map-extra-controls` or the labelled “Draw a route manually” action in the empty online planner; it is not an option in the planner’s route-style selector. While the manual tool is active, the automatic “Point-to-point”/“Round trip” selector is hidden and replaced by a labelled manual-drawing section, a straight-line/no-snapping explanation and “Return to automatic routing”. Returning is disabled offline with an accessible explanation; geometry-replacing changes retain confirmation. “Undo last point” is immediately after the ruler in `map-extra-controls` and visible only while manual mode is editable, including on mobile. The contextual map drawing hint is informational only and hidden in compact layouts as before. Add, move, reorder or delete up to 1,000 points and undo the last point. Routes have `source: manual`; direct segments are calculated locally without routing requests or an ORS API key. There is no road/trail snapping, network connectivity or access validation, or invented elevation. Geometry-replacing mode switches require confirmation; enabling loops retains only the start point, as before.
- Loop discovery with a 2–100 km target: triangular intermediate points, two orientations and at most three routing attempts per orientation (six Directions requests). Candidates are actual routed geometry, deduplicated, closure-checked within 100 m, and ranked by proximity to target distance. Target length and distinct alternatives are not guaranteed.
- Waypoint input uses `latitude, longitude` coordinates or map clicks/draggable pins only. Coordinate input works without an API key; address/place search APIs are not used.
- Geometry-derived distance and estimated moving time. Manual distance is the sum of direct segment lengths; moving duration uses estimates of 18 km/h for cycling and 5 km/h for hiking. ORS directions request heights through the existing API, verified by an approved live request returning complete 3D geometry and two alternatives. Only complete GPX heights or newly marked ORS heights enable ascent/descent and the elevation profile; incomplete, manual and legacy unmarked data do not invent these values. ORS heights are terrain estimates, not measurements on the ground. Hovering the profile or using its accessible position slider highlights the corresponding map point without moving the camera. Separate GPX tracks remain separated in the chart. Opening or closing the profile is remembered for the current app session, including recalculation, added points and Undo/Redo; new geometry does not reopen a profile the user closed.
- Local IndexedDB library: save, name/description edits, reopen, duplicate, filter, and confirmed deletion; unsaved route-discard warnings. Saved, duplicated and reopened manual routes retain their source and exact points and remain editable without Directions.
- GPX tracks/routes/waypoints import (file selection or drop), segment/point/elevation preservation, original-geometry display, and full geometry export with escaped metadata and sensible filenames. Manual exports contain exactly the manual points in order, without snapping, interpolated points, invented elevations or routing-provider attribution.
- Responsive desktop panel and mobile collapsible sheet, keyboard-focusable shadcn controls, Radix modal focus handling, persisted light/dark/system themes, useful loading/error states.
- Installable manifest and production service-worker app shell. Saved routes, GPX export and manual calculations work offline after the initial online visit; basemaps still require online resources, and automatic Directions routing and loop discovery require network access.

## Route schedules, comparison and climb analysis

**Route schedule** stores a local departure date/time and whole-minute pauses (0–10,080 minutes) at individual route waypoints. Arrivals use the personal **moving-only** estimate distributed by actual distance along the geometry. Pauses apply after arrival, including the start and finish; they replace aggregate stops **for the schedule only**, not the existing statistics model. Local calendar arithmetic shows next-day arrivals but intentionally does not apply timezone or daylight-saving transitions. Heights and speed may vary along the route, so these are planning estimates, not navigation predictions. Waypoints must match the route in order within 100 m; unmatched points, disconnected tracks and calendar overflow produce unavailable arrivals rather than invented connectors. Routes without usable ordered waypoints cannot show intermediate arrivals. Schedule fields survive library save/reopen/duplicate, drafts, history and JSON backups; timing edits and timing Undo/Redo do not request routing or replace geometry. GPX remains geometry/waypoint exchange, not a schedule backup.

Time inputs and limitations, climb detection rules and arrival assumptions use consistent collapsed disclosures; the main panel prioritizes metrics and results. Climb analysis has the same 16 px section spacing as the schedule, with its minimum length/gain criteria on a muted line below the heading rather than a floating badge. Their arrows share one alignment and mobile summaries have 44 px touch targets. Waypoint actions use the same labelled outline-button layout on desktop, tablet and mobile: **Add a stop** occupies a full row above equally sized **Reverse** and **Clear stops** actions. Labels wrap without clipping and targets are at least 44 px tall. A lone clear action fills the row; at the stop limit the add action is omitted, and empty loop toolbars are hidden. Deletion still requires confirmation.

In **My routes**, select **2–3 different saved routes** and choose **Compare routes**. The comparison dialog overlays their original geometry in matching legend colors and lists activity, distance, eligible ascent/descent, original saved duration and source. Its map fills the comparison frame on desktop and mobile, inherits the current basemap and does not expose a separate map-style switcher. Missing heights are not estimated; durations for different activities are not directly comparable, and the comparison is not a personal-time prediction. Separate track segments remain separate and direct/manual sections use dashed lines. Selection survives library filters, with a notice for hidden selections. Closing comparison preserves the mounted editor, its unsaved changes and camera; comparison camera movements do not replace the saved editor view. Metrics remain available offline, but basemap loading still requires network access.

**Climb analysis** lists sustained climbs only for complete finite GPX heights or marked ORS elevation geometry. Each climb needs at least **300 m horizontal length and 20 m net height gain**. Descents greater than **3 m** split climbs; smaller drops are ignored. Interior flat sections count toward length, edge flats do not. Track gaps and stationary points split climbs and are never connected. Displayed ascent is filtered **net gain**, and average grade is net gain divided by horizontal length, not maximum slope. Selecting a climb highlights its original segment on the map without moving the camera; selection clears when route geometry changes or becomes stale. ORS terrain heights are estimates, not ground measurements; these thresholds are transparent heuristics, not safety or difficulty ratings.

## Saving, recovery and history

- The library and a single current draft are separate IndexedDB records. Debounced draft autosaving retains ordered stops, mode/activity, names, description, current geometry/statistics/source, editable state, route identity and current personal time settings. Loading and request controllers are not serialized. Pending changes are also flushed when the page becomes hidden; closing a tab cannot guarantee an asynchronous write completes.
- On startup, a draft offers **Restore draft** or **Delete draft**. Recovery does not reroute a ready snapshot, including GPX tracks with disconnected segments and heights. Saving a route or discarding the current work clears its associated draft; late writes/deletes must not replace newer work. Storage errors are reported without disabling the editor.
- Preferences are independent of drafts: map style and camera, language, light/dark/system appearance, activity/mode, loop target, per-activity speeds, stops, planner panels, library search/filters/sort. Camera saves after movement ends, not on animation frames. Existing theme/language/camera storage remains compatible. **Reset settings** requires confirmation and does not delete drafts or library routes.
- Opening a chosen route fits that route; draft recovery restores the editor; ordinary startup uses the last preferences/camera, then existing regional defaults on first use. Geolocation is only requested by the location button. The blue location dot has a translucent accuracy circle whose radius uses the browser-reported accuracy in meters and scales with map zoom; unavailable or invalid accuracy shows only the dot. The circle is updated on each location request and restored when switching map styles. System appearance continues following the OS. Renders and route recalculation do not repeatedly reposition the camera.
- Undo/Redo keeps up to **50 changes** during the current session: adding, deleting, moving, reordering and reversing stops, and geometry-replacing mode changes. A marker drag is one action. New edits clear redo; opening another route or restoring a draft clears session history. Use buttons or **Ctrl/Cmd+Z** and **Ctrl/Cmd+Shift+Z**; text fields retain their native undo. Ready snapshot geometry is restored without a redundant routing request.
- Click an editable, current route line to insert a stop in route order; hovering previews the insertion. Saved/imported snapshots still require explicit conversion before geometry is replaced; disconnected GPX segments are never implicitly joined. Automatic routes support 25 stops, manual drawing 1,000 points. Clicks and taps add points directly when editing is allowed, on both desktop and mobile; no extra add-points toolbar toggle is shown. Existing pins remain draggable, and map dragging does not insert a point.
- Map pins and stop cards share selection. Cards focus the corresponding map point; pins reveal their card and offer explicit replace/remove/start actions. Scale, north reset, direction arrows and scale-dependent distance markers provide orientation without joining separate tracks. Location requests distinguish permission denial, timeout and unavailable position and frame the accuracy area rather than blindly zooming in. Accuracy remains represented by its map circle and accessible geolocation-button description. Elevation, insertion and stale-route labels do not appear as floating map badges; stale status belongs in the planner.
- Recalculation retains the previous route as visibly stale, but disables saving/export and hides outdated statistics until success. Failure, dismissed notices and interrupted requests never make that geometry current. Stale status is persisted in drafts and restored by Undo/Redo; completed matching routes remain available offline.
- Point alternatives use one ORS request for exactly two automatically connected stops. Provider limits and distinct-alternative availability still apply. Selected and inactive alternatives appear together on the map; loop candidates additionally show their absolute difference from the requested length. Disabled alternative actions explain their prerequisites. Cycling, section, fitness and surface choices use the same translated Radix menu styling, keyboard navigation and focus restoration. Calculation and alternative actions share full-width layout. Error cards separate the message, dismiss control and wrapping recovery actions; retries are disabled while busy or offline. Shared typography uses 14px body/control text, 13px labels and 12px supporting text, with larger headings and metrics retained. Mobile text inputs remain 16px to prevent iOS focus zoom; chart ticks use 12px.

Browser storage is not a permanent backup: eviction, private browsing and clearing site data can remove local work. Export important routes and library backups regularly.

## Library backup and organization

“My routes” opens a separate screen with **Back to map**, preserving the mounted editor and its unsaved route. Edit, delete and import confirmations open as overlay dialogs without expanding the route list. Lazy panel loading also overlays the existing layout rather than moving the map. Library routes support favorites, tags, search, activity/favorite/tag/length filters and the existing sorting choices. Filters combine and persist locally; **Reset filters** clears them. Geometry thumbnails are local SVG paths and never connect separate GPX segments. Mobile stop reorder handles have 44px touch areas with unchanged compact icons and keep explicit reorder alternatives. Short-viewport planner/dialog scrolling and readable input sizes are covered by browser emulation; physical iOS Safari and Android Chrome checks remain necessary. Malformed records are reported and skipped in the displayed list, not automatically deleted; valid records remain usable.

**Download backup** downloads JSON with the envelope `{ "version": 1, "exportedAt": "<ISO timestamp>", "routes": [...] }`. Each route contains its supported metadata, geometry segments, heights, original statistics, favorites and tags. Missing older `favorite` and `tags` values default to `false` and `[]`. It excludes the draft, preferences and API keys. Explanations beside the backup actions distinguish JSON library backups from single-route GPX exchange, and state that routes are browser-local with no cloud copy and can be deleted by clearing browser data. Downloading does not claim the file was successfully stored.

**Restore from backup** validates the document and previews its route count before confirmation. Conflicting IDs can be skipped, replaced, or imported as copies (the default); copies receive fresh route and waypoint identifiers. Import is one IndexedDB transaction: invalid data or a storage failure must not leave partial records. Importing the library does not change the open editor.

Backup bounds: **20 MiB per file**, **1,000 routes**, **100,000 points per route**, and **500,000 points overall**. Coordinates, dates, route statistics and the format version are validated. Unsupported versions are rejected. GPX keeps its separate 10 MiB/100,000-point limits.

## Personal time estimates and offline updates

Enter your measured normal flat-ground average: cycling uses **Personal speed (km/h)**; hiking uses **Walking pace (min/km)**, converted to the same stored km/h value. Existing custom speeds are preserved. Fitness (beginner/regular/trained) changes only climbing allowance and uncertainty, never multiplies measured flat-ground speed. Surface (unknown/paved/mixed/rough) is an explicit choice, never inferred; new/opened routes start unknown, while restored drafts retain their choice. Fitness and activity speeds remain preferences; route-specific surface stays in the existing draft/history.

Personal moving seconds are `saved distance metres / 1000 / speed km/h × 3600 × surface factor + climb seconds`. Stops add `minutes × 60` once to both range endpoints. Original provider durations are displayed independently as **Provider estimate**. For automatic routes only, **Planning reference** is the larger of original provider moving seconds and the personal central moving estimate, plus stops once, rounded up to minutes. This conservative planning estimate (not a guarantee) retains provider road constraints when a fast personal flat-ground pace gives a much shorter estimate; it is not a weighted average or part of the personal heuristic range. GPX/manual routes have no combined planning reference. No rerouting or mutation of original manual/GPX/provider statistics or geometry occurs.

Surface factors are transparent, uncalibrated heuristics: hiking paved 1, mixed 1.10, rough 1.25; cycling paved 1, mixed 1.20, rough 1.50; unknown 1 for both. Only complete finite GPX heights or newly marked ORS heights contribute ascent, derived independently per segment with a 3 m reversal threshold to suppress small oscillations. This is not elevation correction: sustained larger noise can remain, changes below the threshold can be omitted, and original heights/statistics are untouched. Segment gaps never contribute ascent. Missing/incomplete heights add no climb allowance and display a warning; mixed routes with direct sections do not fabricate a complete height profile.

Hiking uses a Naismith-inspired allowance of 6 seconds per metre ascended (600 m/h), multiplied by beginner 1.3, regular 1, trained 0.9. The walking benchmark of 5 km/h plus 1 minute per 10 m ascent is documented in [UK regulations](https://www.legislation.gov.uk/uksi/2004/1309/regulation/2/made) and [Naismith’s rule](https://en.wikipedia.org/wiki/Naismith%27s_rule); Roamlet substitutes your measured flat-ground pace. Fitness factors are heuristics, not part of that reference. Cycling separately uses rough ascent rates of 300/450/600 m/h by fitness; this is not Naismith’s walking rule or a physiological prediction. Neither activity receives a downhill speed bonus.

Ranges are **heuristic planning ranges, not confidence intervals or guarantees**. Base spread is ±25%/20%/15% by fitness; unknown surface adds 10 percentage points to both sides, missing heights add 20 to the upper side, and manual straight-line distance adds 30 to the upper side. Endpoints round outward to whole minutes. Weather, wind, load and access are not inferred; technical terrain and real path length can still make travel slower. Nonfinite/overflowing estimates are unavailable rather than shown as infinity.

After the first production online visit, the local editor, draft/settings, library, backups, GPX and manual calculations remain available offline. Offline mode shows a connection banner and a dedicated unavailable-map state instead of loading spinners, map controls or provider configuration errors. Automatic routing and geometry-changing automatic edits are disabled; in-flight requests are cancelled. Saved geometry, statistics, elevation already present in GPX, saving and export remain available. The library and statistics are loaded with the initial application rather than fetched on first use, so they also work when an already-open development session goes offline. Manual drawing still accepts coordinates without an online map; drawing directly on the map is unavailable. The offline banner offers a new coordinate-based route from a saved snapshot without modifying the saved original. The planner uses short contextual explanations instead of a second full offline banner. Help distinguishes local features from online map loading/routing and explains the initial online visit requirement; the app does not promise offline navigation. Reconnecting restores the map without automatically recalculating routes or changing planning mode. On small screens the offline workspace scrolls without squeezing or overlapping the planner. Maps and automatic routing still require their providers; network availability alone does not establish provider availability. Only same-origin shell/assets are cached, not third-party maps or routing APIs.

A waiting service-worker update is announced only when an active version already exists; the first installation does not show an update prompt. The prompt is removed when the worker activates. Updating requires confirmation and a successful draft flush before activation/reload; a storage failure prevents a silent reload. If another tab activates the update while the draft is being saved, the confirmed update reloads after saving. Activation failures are reported separately from draft storage failures. Save/export important work before changing versions. Library storage failures and unavailable basemaps offer local/retry actions without discarding the editor.

## Configuration and providers

| Variable         | Meaning                                                                                                                                        |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `ORS_API_KEY`    | Server-only hosted OpenRouteService key, read from root `.env.local` locally or the Vercel server environment. Never exposed through `VITE_*`. |
| `VITE_MAP_STYLE` | Optional http(s) or root-relative style URL; default `/osm-standard.json` (OpenStreetMap raster tiles)                                         |

MapLibre GL JS uses the Standard OpenStreetMap raster map (OSM Carto) by default, defined in `client/public/osm-standard.json`, with 256-pixel tiles from `https://tile.openstreetmap.org/{z}/{x}/{y}.png` at native zooms 0–19. The Light map remains OpenFreeMap Bright (`https://tiles.openfreemap.org/styles/bright`). Saved Standard preferences use the configured provider (OSM by default); saved Light preferences continue to use Bright. Legacy Custom preferences still load the configured provider, displayed as Standard, and subsequent style selections or camera saves persist it as Standard. Missing or unavailable saved styles retain the OSM fallback and warning. `VITE_MAP_STYLE` replaces the former Mapbox-specific style setting and accepts an `http://`, `https://` or root-relative URL (for example `/styles/custom.json`), not a `mapbox://` URL. Use HTTPS-compatible resources on HTTPS deployments. Resources load browser-direct from OSM, OpenFreeMap or the configured providers, independently of the ORS API key. Preserve the sources' visible attribution, including OpenMapTiles credits for OpenFreeMap.

Follow the [OSM tile usage policy](https://operations.osmfoundation.org/policies/tiles/): retain the browser's HTTP cache and valid Referer, do not deploy a policy that strips cross-origin Referer, and do not add tile prefetching, bulk downloads or offline map features. The service worker does not intercept these external tiles. OSM's donation-funded public tile service and OpenFreeMap offer no SLA; use a suitable provider via `VITE_MAP_STYLE` for deployments whose traffic cannot comply with the public service policy. Automated tests intercept tile requests with synthetic images and do not request public OSM tiles.

The browser uses POST `/api/route` with a `profile` and the existing routing body. The server alone uses POST `https://api.heigit.org/openrouteservice/v2/directions/{cycling-regular|cycling-road|cycling-mountain|foot-hiking}/geojson` with headers `Accept: application/geo+json`, `Content-Type: application/json`, and `Authorization: <API key>`. The GeoJSON endpoint requires the GeoJSON response media type; `Accept: application/json` can return HTTP 406 (ORS code 2007). The JSON body includes `{ "coordinates": [[longitude, latitude], ...], "instructions": false, "elevation": true }`, with `options.avoid_features` when selected. Point alternatives add `alternative_routes: { target_count: 2, weight_factor: 1.4, share_factor: 0.6 }` and require exactly two stops. ORS returns a GeoJSON FeatureCollection with LineString geometry and `properties.summary.distance` / `duration` in metres/seconds. Finite returned heights are retained; absent heights are never fabricated. These parameters are documented in the official [ORS request schema](https://github.com/GIScience/openrouteservice/blob/main/ors-api/src/main/java/org/heigit/ors/api/requests/routing/RouteRequest.java) and [alternative-route schema](https://github.com/GIScience/openrouteservice/blob/main/ors-api/src/main/java/org/heigit/ors/api/requests/routing/RouteRequestAlternativeRoutes.java). Address search, a new backend and offline-map downloads are not added.

**Security and deployment:** `ORS_API_KEY` stays in the server environment. Neither the availability endpoint nor route responses expose it; raw upstream errors and metadata are not forwarded. Actual keys must never be committed. Set Vercel Firewall rate limits before public use and monitor ORS account-wide quotas. Origin checks and client-side caches are not abuse prevention. Provider permissions still require verification; see the [ORS restrictions](https://openrouteservice.org/restrictions/).

### Provider scope

OpenStreetMap supplies the Standard raster basemap and OpenFreeMap supplies the Light vector basemap, both rendered by MapLibre GL JS; hosted OpenRouteService supplies automatic cycling/hiking routes only. New online routes have `source: openrouteservice`. Manual routes have `source: manual` and use local direct segments, independent of routing or API-key configuration. They do not validate road/trail connectivity or access; basemap attribution remains visible, but manual GPX exports contain no routing-provider attribution. Loops remain application-generated with at most six requests. Address/place search is removed from this scope; use coordinates or map clicks/drags. Terrain-RGB fetching, decoding, sampling and caching are entirely excluded. Only imported GPX with complete heights supplies elevation statistics/chart; neither ORS nor legacy Mapbox routes display them, even if old snapshots contain sampled heights.

Automatic routing caches exact input/profile/options responses for five minutes (20 entries); requests have a 25-second timeout. The server availability check is not cached. Cancellation, credential, network and service failures remain actionable, with no automatic straight-line fallback. Manual is a separately selected planning mode, not a fallback for failed routing requests. HTTP 401/403 reports key/account-permission guidance; ORS code 2004 reports service limits. Only ORS codes 2009/2010 are recoverable no-route failures in loop search; code 2011 (incompatible parameters) and generic HTTP 400/422 are service failures, not retried as no-route results. There are no application quota dashboards or quota-recovery controls; Firewall rules must be configured externally. Browser-side bounds and caches do not enforce an account-wide budget. Routing availability, quotas and permitted use depend on the deployed account’s current [ORS terms](https://openrouteservice.org/terms-of-service/) and restrictions. OpenFreeMap’s public basemap service provides no SLA.

**Before publication verify current ORS terms, account eligibility, commercial use, local routing storage/caching, GPX export/redistribution permissions and attribution.** Local storage/export is a product feature, not a legal grant from the provider. Legacy Mapbox snapshots retain their original attribution and remain subject to [Mapbox terms](https://www.mapbox.com/legal/tos); migrating providers does not relicense them. Browser automation uses local synthetic styles/geometry, never production fallback data or real API keys. See [third-party licenses and data policies](./THIRD_PARTY_LICENSES.md).

## Architecture

Yarn has one application workspace, `client/`. Root scripts delegate frontend development, build and browser tests to it; `yarn test` also runs server tests. The deployed frontend uses server-only routing functions.

- `client/`: React/TypeScript/Vite app, browser tests, assets and public environment settings.
- `client/src/domain/`: typed route/provider contracts, geometry calculations, bounded GPX parsing/export and Dexie persistence.
- `client/src/services/routing.ts`: same-origin proxy requests, routing profiles and bounded client-side caches.
- `api/`: Vercel routing and availability function entrypoints.
- `server/routing.mjs`: shared server-only validation, ORS requests and response sanitization, also used by Vite local middleware.
- `server/*.test.mjs`: Node tests for server handlers without real provider requests.
- `client/src/components/`: map, statistics, library and dialogs.
- `client/src/App.tsx`: composition of the planner, map, separate library screen and workflow dialogs.
- `client/src/hooks/`: serializable editor state/history, cancellable routing, draft autosaving and confirmed app updates.
- `client/public/sw.js`: revisioned production shell and same-origin assets, including library/statistics code; excludes all third-party map/routing requests.

IndexedDB version 3 adds favorites/tags and a separate draft store without deleting supported routes. The earlier version 2 cleanup removed unsupported retired sources, not supported snapshots. Supported sources are `openrouteservice`, legacy `mapbox`, `gpx` and `manual`; saving, duplicating and reopening retains each source and exact geometry. New ORS exports credit openrouteservice and OpenStreetMap contributors; legacy Mapbox exports retain Mapbox/OSM attribution. Manual/GPX exports make no routing-provider claim. No provider data is relabeled as ODbL-licensed.

Saved and imported routes open as snapshots and are never silently rerouted. Editing a manual snapshot is explicit and recalculates direct segments locally; converting GPX or online snapshots requires confirmation before replacing geometry. Coordinates use `[longitude, latitude, elevation?]`, distances metres and durations seconds. GPX files are bounded to 10 MiB/100,000 points; segment boundaries and standalone waypoints are preserved. HTTPS or localhost is required for the service worker.

## Known limitations

- OpenFreeMap's public basemap service has no SLA. Hosted OpenRouteService availability and quotas depend on the account's current terms; neither provider access nor the renderer migration guarantees route quality or storage/export permissions.
- ORS cycling-regular/foot-hiking profiles are not certified gravel/trail access recommendations. Access restrictions and surface quality depend on geographic data. Surface breakdown is unavailable; travel times are estimates. No terrain heights are fetched; GPX elevation accuracy depends on the imported file.
- Loop targets are approximate. The same network may yield one unique alternative or no viable loop. Loop geometry can be saved/exported unchanged; geometry-replacing mode switches require confirmation. Manual mode calculates new direct segments locally, whereas automatic editing uses Directions. Enabling loops retains only the start point.
- Editing an imported GPX through automatic Directions routing explicitly converts its start/finish into a newly routed path and replaces the original geometry after confirmation. Multi-track gaps are otherwise preserved. A waypoint-only file is importable/saveable/exportable but cannot be converted through this editor.
- GPX export preserves point order, segment boundaries, elevations, route name/description and standalone waypoints. It does not preserve every arbitrary vendor extension, original XML layout, per-point timestamps or separate track names; routes are exported as GPX tracks. Imported activity defaults to Hiking and can be changed.
- No navigation, tracking, cloud backup, direct Strava/Komoot publishing, offline maps or route surface analytics. There is no application backend. Use the destination app/device's officially supported GPX upload workflow.
- Local browser data can be removed by storage eviction, private browsing, or clearing site data; export important routes as backups.
- MapLibre GL JS requires WebGL and online basemap resources, but OpenFreeMap requires no routing API key. A missing ORS key disables only automatic routing and loop discovery; manual calculations work offline independently of the key. Manual routes use straight lines, not road/trail snapping or network/access validation; moving-time estimates are not validated travel times, and no elevations are invented. Map outages are reported, never replaced by fake production content or offline basemaps. On small screens, the route sheet scrolls/collapses to keep the map accessible.
- Production output includes a large map/vendor JavaScript chunk; further lazy loading is a sensible optimization before broader launch.
- Deploy at the origin root with SPA fallback; base-path deployments need corresponding asset/service-worker path configuration.
