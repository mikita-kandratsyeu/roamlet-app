# Route planning

[Back to overview](../README.md)

## Local-first workflows

Roamlet keeps routes, preferences and the current unsaved draft on this device. No account, analytics or cloud synchronization is required; local workflows need no backend. **Export** opens a dialog with the route name, activity, distance, original time estimate, available ascent/descent, and separate counts of track points, GPX segments and waypoints, followed by an editable GPX filename and a download action. Elevation metrics require complete heights and an eligible GPX/ORS source; missing or partial heights are not invented. The summary adapts to small screens. Filename edits do not rename the route or change its geometry; GPX preserves existing track segments, available elevations, and waypoints. Separate collapsed Komoot and Strava guides link to official import instructions: import is manual, with no account connection or automatic upload. The Strava guide describes creating a route on the website, not uploading a completed activity, and notes that route creation may require a subscription. Downloading works offline; opening external help or Komoot requires internet. GPX is not a full backup of the editor or local library. Automatic routes and loops still use the existing OpenRouteService integration; manual drawing, GPX and library operations remain local.

### First-visit disclaimer

Before using the planner on a first visit, a mandatory English/Russian dialog summarizes the safety/access limitations and approximate travel times and elevations. Full warnings remain in **Help → Real data, honest limits**. Only **Understood** (Russian: **Понятно**) continues, with initial focus on that button. There is no close icon, Escape or outside-click dismissal. The dialog uses the existing responsive light/dark styles and precedes any draft-restoration prompt.

Acknowledgement is stored separately from preferences under `roamlet:disclaimer:v1` in localStorage. Subsequent openings in the same browser profile skip it. Clearing browser data brings it back, while resetting preferences does not. If storage is unavailable, confirmation still allows planning for the current opening and a warning explains that it was not saved. Reloading may then show the dialog again. No acknowledgement data is transmitted.

## Implemented workflows

- MapLibre GL JS (maplibre-gl 5.x) map with OpenStreetMap Standard raster tiles by default (`/osm-standard.json`) and an alternate style labeled Light (`https://tiles.openfreemap.org/styles/bright`), with no separate Custom option. The picker order is Standard (map icon), then Light (Bright, sun icon); Russian labels are «Стандартная» and «Светлая». A configured `VITE_MAP_STYLE` provider occupies the Standard slot instead of exposing a user-facing custom-map mode; configuring Bright keeps OSM in the Standard slot. Satellite mode is not exposed. Switching styles preserves the camera and restores actual route geometry and numbered pins. Required OpenStreetMap/OpenMapTiles style-source attribution, zoom/pan, fit-to-route, optional user location, click-to-add, and draggable waypoint pins remain available; no Mapbox renderer logo is needed. Desktop route fitting accounts for the floating planner’s footprint. No unsupported map layers or offline basemap downloads are exposed.
- Initial viewport priority: opened route → locally saved map view → approximate browser timezone/locale region → world overview. Known IANA timezones select a regional view, other supported continent timezones select a wider view; otherwise locale country/language is a fallback. Browser settings are **not actual geolocation** and may be unrelated to the user's position. No IP lookup, inference API, or automatic location permission prompt is used.
- Maps stay in a flat 2D view: pitch is locked to zero for mouse, touch and keyboard gestures, including restored legacy cameras. Rotation around the vertical axis remains available, along with pinch zoom and the reset-north control. Panning stops on release without inertia; inserting a point by dragging a line preserves this pan policy afterward. Double-click/double-tap zoom is disabled, and repeated click events do not add duplicate stops. Map drags and multi-touch gestures suppress point creation through release and a short cooldown.
- Completed map movements save center, zoom, bearing and zero pitch under `roamlet:map-view:v1` in localStorage. Saved views take priority on reload, while opening/importing a route still fits its geometry. Legacy saved tilt is discarded without losing the center, zoom or bearing. Malformed stored views are ignored; blocked/quota-limited storage does not prevent map use and shows a nonfatal save notice. Clearing site data resets the preference.
- Automatic point-to-point routing with up to 50 stops (including start and finish); coordinate/map replacement, reorder, remove, reverse and cancellable recalculation. Cycling offers ORS regular, road and mountain profiles plus a **Gravel** choice that uses the ORS mountain-biking profile; it does not provide gravel-specific routing or verify surface suitability. Hiking uses `foot-hiking`. Avoid-ferries and avoid-steps options apply to automatic sections, not manual lines. These preferences do not guarantee actual surface or access. Client and server enforce the 50-coordinate hosted ORS Directions limit [confirmed by ORS staff](https://ask.openrouteservice.org/t/1728) and also present as `maximum_waypoints: 50` in the [current backend example configuration](https://github.com/GIScience/openrouteservice/blob/main/ors-config.yml). The hosted restrictions page was unavailable when checked on 2026-10-30; account-specific quotas and distance limits still apply, and these sources do not constitute a live request against the deployed account. Existing longer ORS/legacy Mapbox/GPX snapshots remain readable/exportable, but automatic editing requires reducing stops to this limit.
- Point-to-point sections can individually use automatic road/path routing or an explicitly unverified direct line. Adjacent automatic sections are batched to limit requests. Direct geometry remains separate, uses no invented connectors or heights, and is highlighted differently on the map. Outgoing section modes, routing preferences and direct geometry survive drafts, library backups and history; the last stop's outgoing mode is ignored. Reversing preserves the original sections' modes, and inserting a stop inherits the split section's mode. Mixed time combines ORS durations with average-speed estimates for direct sections.
- For an editable point-to-point route, open a section's routing menu and choose **Draw a detour**. The planner temporarily folds away; a compact map toolbar offers only **Done** and **Cancel**, with an unverified-access explanation. Click to append detour points before the fixed end, drag the line to insert points, or move/remove intermediate points. The original route stays visible in gray. Existing map Undo/Redo edits the temporary detour only. No route changes, routing requests or draft/library writes are made by drawing alone. **Done** commits the entire detour as one undoable edit: its sections become direct lines, other sections keep their modes, and endpoint metadata and pauses are retained. The existing mixed-routing pipeline calculates remaining automatic sections. **Cancel** or Escape discards the detour; route changes or lost editing availability also discard it. Drawing is unavailable for offline automatic routes, busy/stale/read-only routes and routes already at the 50-stop limit. Applied detours use the existing draft, save and GPX export pipeline; an unfinished temporary detour is not persisted.
- Entering **Draw a detour** focuses the selected section once, using its routed geometry including bends, not the entire route. Missing section geometry falls back to its two endpoints. The map is resized before fitting the newly expanded viewport, reserves space for the editing toolbar, and permits a close zoom up to level 18. Adding or moving detour points does not repeatedly refit the map. Dragging an existing editable waypoint shows the same orange dashed, unverified straight-line preview as inserting a new point, connecting only its immediate neighbors (one neighbor at the start/finish). Dragged markers use a highlight ring, not a scale animation: scaling MapLibre's translated marker element would displace it from the pointer. The original grab offset is retained without a jump. The route changes only on release. Escape, window blur or loss of editability cancels the move and clears the preview; detour endpoints remain fixed.
- Manual planning is activated by the ruler-icon button in `map-extra-controls` or the labelled “Draw a route manually” action in the empty online planner; it is not an option in the planner’s route-style selector. While the manual tool is active, the automatic “Point-to-point”/“Round trip” selector is hidden and replaced by a labelled manual-drawing section, a straight-line/no-snapping explanation and “Return to automatic routing”. Returning is disabled offline with an accessible explanation; geometry-replacing changes retain confirmation. “Undo last point” is immediately after the ruler in `map-extra-controls` and visible only while manual mode is editable, including on mobile. The contextual map drawing hint is informational only and hidden in compact layouts as before. Add, move, reorder or delete up to 1,000 points and undo the last point. Routes have `source: manual`; direct segments are calculated locally without routing requests or an ORS API key. There is no road/trail snapping, network connectivity or access validation, or invented elevation. Geometry-replacing mode switches require confirmation; enabling loops retains only the start point, as before.
- Loop discovery with a 2–100 km target: triangular intermediate points, two orientations and at most three routing attempts per orientation (six Directions requests), with a 45-second total search budget. The best closed candidate from each orientation is ranked by proximity to target distance; the closest is selected first. Closure is checked within 100 m. Near-duplicate filtering compares 64 equally spaced samples along each route in either direction: at least 90% must be within 100 m and route lengths within 10% of the longer route. This is a geometric heuristic, not a road/access check; original geometry and elevations are unchanged. Cards show actual distance and absolute/signed-percentage deviation from the target. On reaching the time budget, already found closed candidates are shown; if none exist, an actionable timeout is shown. User cancellation discards the search, including partial results. The client aborts the pending proxy request but cannot guarantee that ORS computation stops or quota is refunded. Target length and two distinct alternatives are not guaranteed.
- Waypoint input uses `latitude, longitude` coordinates or map clicks/draggable pins only. Coordinate input works without an API key; address/place search APIs are not used.
- In editable point-to-point and manual routes, drag the route line to insert a waypoint into the section where the gesture started. Mouse, pen and single-touch gestures show an orange dashed straight-line preview and a temporary point; this preview is not road/path-snapped or access-verified. Release inside the map to commit one edit and trigger the existing routing/history pipeline. A click still inserts a point on the original line. Escape, pointer cancellation, a second touch, window blur, release outside the map, or a route/mode change cancels without editing. Existing stop limits and section modes apply. Read-only, comparison and stale routes do not allow line dragging; ordinary map navigation and marker dragging remain available.
- Geometry-derived distance and estimated moving time. Manual distance is the sum of direct segment lengths; moving duration uses estimates of 18 km/h for cycling and 5 km/h for hiking. ORS directions request heights through the existing API, verified by an approved live request returning complete 3D geometry and two alternatives. GPX heights or newly marked ORS heights enable profiles on their known portions. Full-route ascent/descent require complete coverage, while partial planner metrics are explicitly limited to known sections. Manual and legacy unmarked data do not acquire invented values. ORS heights are terrain estimates, not measurements on the ground. Hovering the profile or using its accessible position slider highlights the corresponding map point without moving the camera. Separate GPX tracks remain separated in the chart. Opening or closing the profile is remembered for the current app session, including recalculation, added points and Undo/Redo; new geometry does not reopen a profile the user closed.
- Local IndexedDB library: save, name/description edits, reopen, duplicate, filter, and confirmed deletion; unsaved route-discard warnings. Saved, duplicated and reopened manual routes retain their source and exact points and remain editable without Directions.
- GPX tracks/routes/waypoints import (file selection or drop), segment/point/elevation preservation, original-geometry display, and full geometry export with escaped metadata and sensible filenames. The file picker intentionally has no extension/MIME filter: iOS can otherwise disable GPX files with unrecognized types or duplicate-download names such as `route.gpx 2`. Choose the downloaded GPX; its XML content is validated regardless of its name/type, with the existing 10 MiB and 100,000-point limits. File reading, XML validation, parsing and initial statistics run in a local module Web Worker, without uploading the file. Import shows a cancellable loading state; a newer file, editor changes or leaving the app cancel the old operation, and late results cannot replace the current route. Successful imports still require confirmation before discarding unsaved work. The worker is precached with the production app shell, including for its first offline use. Manual exports contain exactly the manual points in order, without snapping, interpolated points, invented elevations or routing-provider attribution. The export dialog includes a non-interactive mini-map fitted to the exported track, with start/finish markers; an outline remains available when the basemap or WebGL cannot load. The preview does not alter the GPX file.
- Responsive desktop panel and mobile collapsible sheet, keyboard-focusable shadcn controls, Radix modal focus handling, persisted light/dark/system themes, useful loading/error states.
- Installable manifest and production service-worker app shell. Saved routes, GPX export and manual calculations work offline after the initial online visit; basemaps still require online resources, and automatic Directions routing and loop discovery require network access.

## Route schedules, comparison and climb analysis

**Weather at start** is a separate collapsed panel next to Route schedule. Choose a departure date/time there, then explicitly select **Load forecast**. Only the first track coordinate (longitude/latitude, without elevation) is sent directly to [Open-Meteo](https://open-meteo.com/en/docs), without cookies or referrer. Opening the panel, editing dates and planning routes never automatically request weather. No API key, backend or additional dependency is required. The free endpoint is for non-commercial use, subject to [provider limits and terms](https://open-meteo.com/en/pricing); commercial deployments require an appropriate subscription. Attribution links to Open-Meteo and CC BY 4.0 remain visible.

The panel shows temperature, feels-like temperature, precipitation/probability, wind speed/direction/gusts and up to six hourly observations at the start location, beginning with the departure hour. This is not weather along the route. The provider's local timestamps and returned timezone interpret the existing departure wall clock at the start, never in the device timezone. The schedule's timezone/DST semantics are unchanged. Ambiguous/missing daylight-saving hours are not resolved, hourly observations are approximate, and precipitation/gusts describe the preceding hour. Missing values remain unavailable. Dates outside the returned forecast (up to 16 days ahead) do not substitute today's weather.

The device-local `roamlet:weather:v1` localStorage cache keeps at most eight start locations and forecasts, usable for up to 24 hours. Entries under 30 minutes old are reused after an explicit load; **Refresh forecast** requests an update. Older or offline copies are labeled with their load time in the start timezone. Expired entries are excluded from reads and pruned on later writes, not by a background deletion job. Unavailable storage does not block weather. Changing the start, departure or route invalidates the displayed selection and cancels pending work, with late responses ignored. Network failures retain a clearly labeled cached copy when available and offer retry. Failed loads/refreshes and explicit offline load attempts show one dismissible Sonner error notification, without duplicating the error inside the panel; cancelled or stale requests do not notify. Forecasts are not saved inside routes, drafts, JSON backups or GPX and never change geometry, statistics or timing. Manual planning, the library and GPX remain usable without weather or network access.

**Route schedule** stores a local departure date/time and whole-minute pauses (0–10,080 minutes) at individual route waypoints. Arrivals use the personal **moving-only** estimate distributed by actual distance along the geometry. Pauses apply after arrival, including the start and finish; they replace aggregate stops **for the schedule only**, not the existing statistics model. Local calendar arithmetic shows next-day arrivals but intentionally does not apply timezone or daylight-saving transitions. Heights and speed may vary along the route, so these are planning estimates, not navigation predictions. Waypoints must match the route in order within 100 m; unmatched points, disconnected tracks and calendar overflow produce unavailable arrivals rather than invented connectors. Routes without usable ordered waypoints cannot show intermediate arrivals. Schedule fields survive library save/reopen/duplicate, drafts, history and JSON backups; timing edits and timing Undo/Redo do not request routing or replace geometry. Date and pause validation messages occupy their own row below the input, wrapping without covering the control on narrow screens in either language. The departure field keeps the native device date/time picker, constrains its editor to the available width and uses a 16 px font on touch devices to avoid focus zoom. GPX remains geometry/waypoint exchange, not a schedule backup. Geometry matching is deferred until departure and moving time are valid and reused across date/pause/speed edits; unrelated map/profile interactions do not recalculate the schedule.

Time inputs and limitations, climb detection rules and arrival assumptions use consistent collapsed disclosures; the main panel prioritizes metrics and results. Climb analysis has the same 16 px section spacing as the schedule, with its minimum length/gain criteria on a muted line below the heading rather than a floating badge. Their arrows share one alignment and mobile summaries have 44 px touch targets. Waypoint actions share one row on desktop, tablet and mobile: the outlined **Add a stop** action keeps its text, while **Reverse** and **Clear stops** use 44×44 px icon buttons with accessible names and tooltips. The clear icon retains its destructive color. At the stop limit the add action is omitted; a lone clear icon stays right-aligned, and empty loop toolbars are hidden. Deletion still requires confirmation.

The library keeps search/sort, backup tools, filters and comparison controls in consistent bordered surfaces. Backup actions remain directly available while their storage explanation starts collapsed. The content grows to 1600 px on wide screens; route cards use one column on narrow screens, two on medium screens, three from 1160 px and four from 1480 px, without stretching individual cards across the whole monitor. Filter inputs and actions share 44 px touch targets; the distance range and favorites move to separate rows on narrow screens.

In **My routes**, select **2–5 different saved routes** and choose **Compare routes**. Comparison opens a full-screen in-app map workspace, not a browser fullscreen session. The header follows the library screen's layout and typography, with its title on the left and return action on the right. Both headers span the viewport with fixed 24 px side padding on desktop and 16 px on narrow mobile screens; only the library content remains width-constrained. A floating left desktop panel matches the planner's width, spacing, surface, rounded corners and shadow; a collapsible mobile bottom sheet retains the same visual language. Both list numbered, color-coded route cards with activity, distance and original saved duration. An eye control toggles visibility; the selected card is highlighted as a whole. On hover-capable devices, hovering the route title highlights the whole card rather than an inset title button without selecting it; the eye keeps separate hover feedback. On desktop collapsing removes the panel completely, leaving only floating reopen and overview buttons, while mobile retains a compact bottom bar with the planner's 16 px/600 title and neutral 44×44 px controls. The desktop map fills the workspace and fits routes into the unobstructed space beside the panel. Select a route to focus its geometry, toggle its visibility (at least one remains visible), or choose **Show all routes** to restore the combined overview. Expand **Route statistics** for activity, distance, eligible ascent/descent, original saved duration and source. The panel can be collapsed without remounting the map; controls and map attribution remain outside it. The map inherits the current basemap and does not expose a separate map-style switcher or editing tools such as manual drawing, Undo or Redo. Missing heights are not estimated; durations for different activities are not directly comparable, and the comparison is not a personal-time prediction. Separate track segments remain separate and direct/manual sections use dashed lines. Selection survives library filters, with a notice for hidden selections. The compact library selection widget shows a 0–5 counter, state-specific guidance and numbered color-coded route chips. Up to five distinct routes can be compared; additional selection is disabled until a selected route is removed. All five routes retain unique palette colors in the legend, statistics and map. Its primary compare action sits beside the summary on desktop and below the selection on mobile; clear selection remains accessible as a named icon on mobile. Selected-route buttons remove a route from comparison and retain a minimum 44×44px touch target with a distinct 20px close icon, including for wrapped route names. The comparison panel uses the planner's thin, theme-aware scrollbar with a transparent track. **Back to routes** or Escape returns to the library with its selection, filters and scroll position intact, restoring focus to **Compare routes**. The separate **Back to planner** header action closes both comparison and the library, returning directly to the current planner without creating a new route or discarding unsaved edits. Closing comparison preserves the mounted editor, its unsaved changes and camera; comparison camera movements do not replace the saved editor view. Metrics remain available offline, but basemap loading still requires network access.

**Climb analysis** lists sustained climbs only for complete finite GPX heights or marked ORS elevation geometry. Each climb needs at least **300 m horizontal length and 20 m net height gain**. Descents greater than **3 m** split climbs; smaller drops are ignored. Interior flat sections count toward length, edge flats do not. Track gaps and stationary points split climbs and are never connected. Displayed ascent is filtered **net gain**, and average grade is net gain divided by horizontal length, not maximum slope. Selecting a climb highlights its original segment on the map without moving the camera; selection clears when route geometry changes or becomes stale. ORS terrain heights are estimates, not ground measurements; these thresholds are transparent heuristics, not safety or difficulty ratings.

Calendar actions are available inside **Route schedule**. Google publication requires a connected Calendar session, internet and a saved current route; creating/updating the event always needs explicit preview confirmation. Changes do not trigger routing or calendar synchronization. Calendar controls are hidden before connection or after explicit disconnection, but remain available for reconnection after expiry. **Export calendar (.ics)** remains independent of the connector. Calendar timestamps use an explicitly reviewed IANA timezone and elapsed duration, unlike the schedule's floating wall-clock arrival display. See [Calendar connections](connections.md#google-calendar) and [ICS export](exports.md#calendar-events-ics) for limits and privacy.

## Partial elevation profiles

Adding manual sections to an automatic route retains the ORS heights on the remaining routed sections. Direct sections stay two-dimensional. The elevation profile and slope layer show only contiguous known-height portions, with gaps across unknown heights, GPX segment boundaries and stationary height jumps. The chart's horizontal axis still includes the distance of manual sections, so known portions keep their correct positions along the whole track.

For partial profiles, planner gain/loss labels explicitly say **known sections**. These numbers are computed from known edges for display, not stored as whole-route elevation totals. Library snapshots, duplication, drafts, JSON backups and GPX retain the original known heights and unknown portions without interpolation. Full-route gain/loss, complete-profile climb analysis, elevation-based time allowances and export-summary totals remain unavailable when coverage is incomplete. ORS heights remain estimates, and legacy routes without confirmed elevation provenance are not silently relabeled.

## Route slope coloring

In **More map tools → Color route by slope**, coloring starts enabled when the route has at least one drawable section with known GPX or confirmed ORS heights; turn it off in the menu if desired. Colors describe local estimated grade rather than the average grade of an entire detected climb. Flat sections (−1% to +1%) are green, descents blue, and increasingly steep ascents yellow, orange and red, with color extremes at −10% and +10%. The legend and an estimate warning stay in the tools menu rather than covering the map.

Grades use horizontal distance and a nominal 100 m window, truncated at each drawable run's boundaries. Sparse tracks use original points bracketing the window, so their effective window can be longer. No interpolated heights, saved-data changes or additional network requests are introduced. Track gaps and consecutive zero-horizontal-distance edges separate runs, so stationary height jumps do not create artificial grades. Missing heights split runs rather than being filled in. A track with no known drawable run, or invalid coordinates, has no slope coloring.

Rendering is bounded to 2,000 colored features while retaining original drawable geometry. Large tracks group neighboring edges, reducing color detail, not altering the saved track. More independent drawable runs than the feature limit cannot be safely joined and make coloring unavailable. Heights can be noisy or estimated: colors are planning aids, not ground measurements, accessibility classifications or safety assessments. Manual routes and retired Mapbox snapshots are not given invented slopes.

## Personal time estimates

For cached-shell behavior and updates, see [PWA and offline behavior](offline.md).

Enter your measured normal flat-ground average: cycling uses **Personal speed (km/h)**; hiking uses **Walking pace (min/km)**, converted to the same stored km/h value. Existing custom speeds are preserved. Fitness (beginner/regular/trained) changes only climbing allowance and uncertainty, never multiplies measured flat-ground speed. Surface (unknown/paved/mixed/rough) is an explicit choice, never inferred; new/opened routes start unknown, while restored drafts retain their choice. Fitness and activity speeds remain preferences; route-specific surface stays in the existing draft/history.

Personal moving seconds are `saved distance metres / 1000 / speed km/h × 3600 × surface factor + climb seconds`. Stops add `minutes × 60` once to both range endpoints. Original provider durations are displayed independently as **Provider estimate**. For automatic routes only, **Planning reference** is the larger of original provider moving seconds and the personal central moving estimate, plus stops once, rounded up to minutes. This conservative planning estimate (not a guarantee) retains provider road constraints when a fast personal flat-ground pace gives a much shorter estimate; it is not a weighted average or part of the personal heuristic range. GPX/manual routes have no combined planning reference. No rerouting or mutation of original manual/GPX/provider statistics or geometry occurs.

Surface factors are transparent, uncalibrated heuristics: hiking paved 1, mixed 1.10, rough 1.25; cycling paved 1, mixed 1.20, rough 1.50; unknown 1 for both. Only complete finite GPX heights or newly marked ORS heights contribute ascent, derived independently per segment with a 3 m reversal threshold to suppress small oscillations. This is not elevation correction: sustained larger noise can remain, changes below the threshold can be omitted, and original heights/statistics are untouched. Segment gaps never contribute ascent. Missing/incomplete heights add no climb allowance and display a warning; mixed routes with direct sections do not fabricate a complete height profile.

Hiking uses a Naismith-inspired allowance of 6 seconds per metre ascended (600 m/h), multiplied by beginner 1.3, regular 1, trained 0.9. The walking benchmark of 5 km/h plus 1 minute per 10 m ascent is documented in [UK regulations](https://www.legislation.gov.uk/uksi/2004/1309/regulation/2/made) and [Naismith’s rule](https://en.wikipedia.org/wiki/Naismith%27s_rule); Roamlet substitutes your measured flat-ground pace. Fitness factors are heuristics, not part of that reference. Cycling separately uses rough ascent rates of 300/450/600 m/h by fitness; this is not Naismith’s walking rule or a physiological prediction. Neither activity receives a downhill speed bonus.

Ranges are **heuristic planning ranges, not confidence intervals or guarantees**. Base spread is ±25%/20%/15% by fitness; unknown surface adds 10 percentage points to both sides, missing heights add 20 to the upper side, and manual straight-line distance adds 30 to the upper side. Endpoints round outward to whole minutes. Weather, wind, load and access are not inferred; technical terrain and real path length can still make travel slower. Nonfinite/overflowing estimates are unavailable rather than shown as infinity.

## Known limitations

- OpenFreeMap's public basemap service has no SLA. Hosted OpenRouteService availability and quotas depend on the account's current terms; neither provider access nor the renderer migration guarantees route quality or storage/export permissions.
- ORS cycling-regular/foot-hiking profiles are not certified gravel/trail access recommendations. Access restrictions and surface quality depend on geographic data. Surface breakdown is unavailable; travel times are estimates. No terrain heights are fetched; GPX elevation accuracy depends on the imported file.
- Loop targets are approximate. The same network may yield one unique alternative or no viable loop. Loop geometry can be saved/exported unchanged; geometry-replacing mode switches require confirmation. Manual mode calculates new direct segments locally, whereas automatic editing uses Directions. Enabling loops retains only the start point.
- Editing an imported GPX through automatic Directions routing explicitly converts its start/finish into a newly routed path and replaces the original geometry after confirmation. Multi-track gaps are otherwise preserved. A waypoint-only file is importable/saveable/exportable but cannot be converted through this editor.
- GPX export preserves point order, segment boundaries, elevations, route name/description and standalone waypoints. It does not preserve every arbitrary vendor extension, original XML layout, per-point timestamps or separate track names; routes are exported as GPX tracks. Imported activity defaults to Hiking and can be changed.
- No navigation, tracking, cloud backup, direct Strava/Komoot publishing, offline maps or route surface analytics. There is no application backend. Use the destination app/device's officially supported GPX upload workflow.
- Local browser data can be removed by storage eviction, private browsing, or clearing site data; export important routes as backups.
- MapLibre GL JS requires WebGL and online basemap resources, but OpenFreeMap requires no routing API key. A missing ORS key disables only automatic routing and loop discovery; manual calculations work offline independently of the key. Manual routes use straight lines, not road/trail snapping or network/access validation; moving-time estimates are not validated travel times, and no elevations are invented. Map outages are reported, never replaced by fake production content or offline basemaps. On small screens, the route sheet scrolls/collapses to keep the map accessible.
- Production output includes a large map/vendor JavaScript chunk; further lazy loading is a sensible optimization before broader launch.
- Deploy at the origin root with SPA fallback; base-path deployments need corresponding asset/service-worker path configuration.
