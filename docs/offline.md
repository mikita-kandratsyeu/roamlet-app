# PWA installation and offline behavior

[Back to overview](../README.md)

## Installing Roamlet (PWA)

On the HTTPS production site, use the browser's **Install app** / **Install Roamlet** action (Chrome/Edge on desktop or Android). In Safari on iPhone/iPad, use **Share → Add to Home Screen**; on macOS Safari versions that support it, use **File → Add to Dock**. Availability and wording depend on the browser and OS; a desktop shortcut is not always an installed standalone app.

The installed app is named **Roamlet**. The [web manifest](../client/public/manifest.webmanifest) defines a stable root identity, start URL and scope, with branded 192/512 px PNG icons and a separate opaque maskable icon whose artwork stays inside the central 80%-diameter safe circle. [HTML metadata](../client/index.html) also supplies the Roamlet title, PNG/SVG favicons and an opaque 180 px Apple touch icon. PNGs are rasterized from the existing [brand SVG](../client/public/icon.svg); the maskable version adds safe padding. The service worker precaches the manifest and all icons along with the offline shell. Local routes and GPX remain available offline; basemaps and automatic routing still need a connection.

Open **Menu → App on this device** (Russian: **Меню → Приложение на устройстве**) for installation, offline readiness and local-data protection. The dialog reuses existing responsive light/dark dialogs and does not add persistent map overlays or periodic notifications. **Install app** appears only when the browser supplies an installation prompt, with a collapsed manual guide for iOS/iPadOS, Android/Chrome/Edge and macOS Safari otherwise. Standalone windows show an installed-app status. Dismissing installation does not interrupt planning.

**Ready to work offline** is shown only after the active production service worker confirms a complete cached shell. Preparing, unverified/error, unsupported-browser and development states remain distinct. Failed preparation offers an online retry without activating a waiting update during editing. Retrying can repair an incomplete current-version cache after verifying the deployed worker revision, with resources staged before publication. If the deployed version differs, launch/reload again to apply the waiting update rather than mixing new HTML with old assets. An incomplete installation or a worker that cannot confirm readiness is not reported as ready. The dialog separates offline local workflows from online map/routing/cloud functions. Readiness confirms the cached shell now, not permanent storage, map downloads or navigation.

Storage protection is requested only by pressing **Request storage protection**, using `navigator.storage.persist()` when supported. The dialog distinguishes granted, browser-managed, declined, unsupported and unchecked states. After a grant or denial, it shows one compact status without repeating request instructions or the request button; a failed check/request still allows retry. Explicit installation, storage and offline-retry failures use Sonner notifications; storage denial produces one warning, while passive startup checks and successful requests do not produce notifications. A grant reduces automatic eviction risk but cannot prevent clearing site data or guarantee a permanent backup. Backup details remain in a collapsed disclosure, with **Open My routes** always reachable in the dialog footer and leading to the existing library and JSON backup controls. No automatic cloud backup, extra permissions on startup or new data transmission is added.

A waiting update is explained only inside this dialog and applies on the next startup/reload, never by forcing an editing window to reload. After deploying a branding update, open the app online and launch/reload it again once the update is ready. Some platforms retain the old installed name/icon; reinstalling the shortcut/app may be necessary. Export a library backup first, do not clear site data, and keep the same production origin: installation does not provide cloud backup, and browser storage can be removed by the browser or OS.

Physical-device release checks (browser emulation is not a substitute):

- Install from HTTPS on an iPhone/iPad and Android, then launch from the home screen. Confirm standalone status and the correct icon/name.
- Confirm offline readiness online, close/reopen offline, and open/export a saved route. Verify that missing maps/automatic routing are explained without preventing local work.
- Test portrait/landscape, notches/home indicators, the on-screen keyboard, dialog scrolling and reachable 44 px actions in both languages/themes.
- Background/foreground and relaunch with an unsaved draft. Verify restoration and a waiting update without interrupting editing.
- Download/share GPX and JSON backups and restore a backup. Complete optional OAuth from the installed app, return to it, and verify that the existing local library is still accessible. Check the actual browser/OS storage context rather than assuming it is shared.
- Exercise supported storage protection and declined/unsupported paths. Never clear production site data just to test without exporting important work first.

## Offline workflows and updates

After the first production online visit, the local editor, draft/settings, library, backups, GPX and manual calculations remain available offline. Offline mode shows a connection banner and a dedicated unavailable-map state instead of loading spinners, map controls or provider configuration errors. Banner actions have at least 44 px touch targets and grow with wrapped labels; narrow screens stack them instead of clipping text, and a single remaining action fills its mobile row. Automatic routing and geometry-changing automatic edits are disabled; in-flight requests are cancelled. Saved geometry, statistics, elevation already present in GPX, saving and export remain available. The library and basic statistics are loaded with the initial application, so they also work when an already-open development session goes offline. The interactive elevation chart and Recharts load separately only when an eligible profile is expanded; the collapsed preview remains in the initial application. The production service worker precaches this chart chunk for first offline use after installation completes. Without a service worker, a chart not previously loaded needs internet; a failed load offers a panel retry without blocking local editing, statistics or GPX export. Manual drawing still accepts coordinates without an online map; drawing directly on the map is unavailable. The offline banner offers a new coordinate-based route from a saved snapshot without modifying the saved original. The planner uses short contextual explanations instead of a second full offline banner. Help distinguishes local features from online map loading/routing and explains the initial online visit requirement; the app does not promise offline navigation. Reconnecting restores the map without automatically recalculating routes or changing planning mode. On small screens the offline planner keeps distinct compact, planning and expanded sizes, including short/landscape viewports. The compact header stays at the bottom of the workspace without a blank area below it; the unavailable-map message fills the remaining space and scrolls independently when necessary. Open planner fields scroll within the panel, while exceptionally short workspaces may also scroll to keep controls reachable. Maps and automatic routing still require their providers; network availability alone does not establish provider availability. Only same-origin shell/assets are cached, not third-party maps or routing APIs.

The service worker never intercepts `/api` or `/api/*` requests, including document navigations. OAuth sign-in and callback redirects must reach the server rather than receiving the cached app shell; API responses are not stored in the shell cache. After deploying a fix to an existing installation, open the main app URL online to let the replacement worker install, then reload or close all app tabs and reopen. Do not clear site data: it contains local routes and drafts.

App updates do not show a notification or interrupt editing. A fully installed waiting service worker is activated on the next opening or manual page reload, before the editor mounts; that startup reloads once to use the matching new shell. Updates discovered during a session wait until a later startup or until all app tabs close. Other open tabs are never automatically reloaded, and their old cached chunks remain available. Startup waits at most three seconds; registration/activation failures leave the existing editor available without an update prompt or a delayed reload. Already-saved drafts, routes and settings remain local and can be restored as before. Save/export important work before manually reloading or closing the app. Library storage failures and unavailable basemaps offer local/retry actions without discarding the editor.
